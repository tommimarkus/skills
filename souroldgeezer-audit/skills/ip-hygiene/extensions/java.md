# Java IP Hygiene Extension

Load this pack when the reviewed files include `*.java`, a Maven `pom.xml`, or
a Gradle build script (`build.gradle`, `build.gradle.kts`, `settings.gradle`).
It adds the language-specific facts
[source-code.md](../references/source-code.md) defers to each language; it
does not restate that file's four classes, notice-survival transformation
list, or generated-material split.

## Detection signals

`*.java` files; a `pom.xml` (Maven) or `build.gradle`/`build.gradle.kts`/
`settings.gradle`/`settings.gradle.kts` (Gradle) in the reviewed tree; a
`target/` (Maven) or `build/` (Gradle) output directory when its contents are
in scope.

## Comment and doc-comment syntax

Line comments use `//`; block comments use `/* ... */`. The doc-comment
convention is Javadoc: a `/** ... */` block immediately preceding the class,
interface, method, or field it documents, using `@`-tagged fields such as
`@author`, `@since`, and `@see`. `source-code.md`'s "Notices and headers"
class applies to `@author`/`@copyright`-style Javadoc tags specifically, while
its "Copied doc-comment prose" class applies to the narrative body of a
Javadoc block, most often where upstream vendor API documentation prose has
been pasted into a wrapper or reimplementation's own Javadoc.

## Header placement and ordering

A licence header or `SPDX-License-Identifier` line is a leading `//` or
`/* */` comment block and must precede the `package` declaration, which is
itself required to be the first non-comment statement in the file. A
package-level licence or notice has a dedicated home: `package-info.java`, a
file whose sole content is a package-level Javadoc block followed by the
`package` statement, with no class body. Treat a `package-info.java` missing
from a package directory that otherwise carries per-file headers as a gap in
package-level notice coverage, not evidence the package is unlicensed.

## Ecosystem licence metadata

Maven's `pom.xml` declares licence under a `<licenses>` element holding one or
more `<license>` entries (`<name>`, `<url>`, and optionally `<distribution>`).
Gradle has no equivalent native field; a Gradle project's published licence
metadata, when present, is set through the `maven-publish` plugin's POM
customization block and ends up in the same `<licenses>` shape once
published. Neither declaration is itself the notice: per `source-code.md`'s
notices class (`IP-LIC-1`), a `pom.xml` licence entry states the project's
own declared terms and does not establish or substitute for a dependency's or
vendored file's own header.

## Vendoring conventions

Java's ecosystems (Maven Central, Gradle) resolve dependencies at build time
rather than vendoring source into the repository, so there is no single
canonical vendored-source directory comparable to other ecosystems. The two
patterns that do commit third-party material are a `lib/` directory holding
checked-in third-party `.jar` files bypassing normal dependency resolution,
and dependency **relocation** during shading (the shade/shadow plugins
rewriting a dependency's package names into the consuming project's own
namespace) — relocated code is still third-party material and keeps its
notice obligations despite no longer looking like an external dependency.

## Generated-code banners

Annotation-processor output (Dagger, MapStruct, Immutables, and similar) and
JAXB/`xjc`-generated classes carry a `@Generated` annotation
(`javax.annotation.Generated` or its `jakarta.annotation.Generated`
successor) naming the generator, often paired with a leading comment stating
the class was generated and should not be edited. Protocol Buffers'
`protoc`-generated Java sources open with a comment naming the source
`.proto` file and stating the code was generated by the protocol buffer
compiler. Both Maven (`target/generated-sources/`) and Gradle
(`build/generated/`) route generated output to a build directory outside
normal source control by convention. Apply `source-code.md`'s
generator/input/output split (`IP-SRC-5`) to whichever banner is present.

## Notice-survival mechanics

Java source comments are discarded at compilation and carry no obligation
into the compiled `.class` file, so the source-level minification concern
other languages have does not apply here; the equivalent risk sits at the
**artifact** level. Building a shaded or fat jar (Maven Shade Plugin, Gradle
Shadow plugin) merges the `META-INF/` contents of every constituent
dependency into one jar, and a naive merge is last-writer-wins: each
dependency's `META-INF/LICENSE` and `META-INF/NOTICE` file has the same path,
so later entries silently overwrite earlier ones unless the build is
configured with an aggregating transformer (for example, the Shade Plugin's
notice-resource transformer, or Shadow's equivalent merge strategy) that
concatenates rather than replaces. This is the concrete `IP-LIC-5` case for
this ecosystem: confirm the build declares an aggregating transformer before
concluding a multi-dependency fat jar's notices survived assembly.

## Mark surfaces

The Maven `groupId`/`artifactId` (or Gradle `group`/project name) is the
package's identity on Maven Central and the most common location for a
third-party organization or project mark to appear verbatim. `MANIFEST.MF`
attributes such as `Implementation-Title` and `Implementation-Vendor`, a
`User-Agent` string literal set on an HTTP client, and CLI `--version`/banner
strings are the other recurring surfaces, per `source-code.md`'s "Marks in
code" class (`IP-MARK-1`, `IP-MARK-2`).

## Criteria

This pack carves out no core criterion and adds none; it applies the core
`IP-LIC-*`, `IP-SRC-*`, `IP-COPY-*`, and `IP-MARK-*` criteria via the facts
above. No `java.IP-*` numbered criterion is defined.
