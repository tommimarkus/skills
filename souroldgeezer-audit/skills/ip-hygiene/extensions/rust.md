# Rust IP Hygiene Extension

Load this pack when the reviewed files include `*.rs` or a `Cargo.toml`. It
adds the language-specific facts [source-code.md](../references/source-code.md)
defers to each language; it does not restate that file's four classes,
notice-survival transformation list, or generated-material split.

## Detection signals

`*.rs` files; `Cargo.toml` or `Cargo.lock` in the reviewed tree; a `target/`
build-output directory or a `vendor/` directory when its contents are in
scope.

## Comment and doc-comment syntax

Line comments use `//`; block comments use `/* ... */`. Rust has two
doc-comment forms rather than one: `///` (outer doc comments), which precede
and document the item immediately below them, and `//!` (inner doc
comments), which document the enclosing item — a module or, at the very top
of a file, the whole crate or file-as-module. `source-code.md`'s "Copied
doc-comment prose" class applies to the body of either form, most often where
upstream API documentation prose has been pasted into an `///` block for a
reimplemented or wrapped function.

## Header placement and ordering

`//!` inner doc comments and inner attributes (`#![...]`, such as
`#![allow(...)]` or `#![no_std]`) must appear before any item definition in
the file, and by convention sit at the very top. This directly constrains
where a licence header can go: a leading `//`/`/* */` licence header or
`SPDX-License-Identifier` line placed above the `//!` block is the ordinary
placement and does not conflict with it, but a header placed **between** the
`//!` block and the first item is easy to mistake for stray commentary rather
than the file's own notice — check both possible positions before concluding
a header is absent. Rust source files do not carry a shebang.

## Ecosystem licence metadata

`Cargo.toml`'s `[package]` table declares licence via a `license` field (an
SPDX licence expression, most often supporting the ecosystem's prevailing
dual-licence offer) or a `license-file` field pointing at a bundled licence
file when the terms have no SPDX identifier. crates.io requires one or the
other to be present for publication. Neither field is itself the notice: a
manifest `license` value states the whole published crate's declared terms
and does not confirm any individual file's header, per `source-code.md`'s
notices class (`IP-LIC-1`). The dual MIT/Apache-2.0 offer this field commonly
encodes is licence layering already covered by core `IP-LIC-4`; do not
re-derive it here — confirm the reviewer records which offered licence is
selected, since a dual offer is a choice, not a single value.

## Vendoring conventions

The `cargo vendor` command is the ecosystem's standard vendoring mechanism:
it writes a full copy of every dependency crate's source into a `vendor/`
directory and is normally paired with a `.cargo/config.toml` source
replacement entry pointing dependency resolution at that directory instead of
the network registry. A committed `vendor/` directory is unambiguous evidence
of vendored third-party code carrying that dependency's full licence and
notice obligations into the repository; it is distinct from `Cargo.lock`,
which pins dependency versions without vendoring their source.

## Generated-code banners

`build.rs` build-script output lands under a Cargo-managed `OUT_DIR` inside
`target/` and is typically pulled into the crate via an `include!()` macro
rather than committed as a source file. `bindgen`-generated FFI bindings open
with a comment stating the file was automatically generated by `rust-bindgen`
and should not be edited by hand. Code generated by `prost`/`tonic-build` from
`.proto` definitions likewise opens with a comment naming the generator and
the source schema. Apply `source-code.md`'s generator/input/output split
(`IP-SRC-5`) to whichever banner is present, and treat `build.rs` itself as
the generator whose own licence is a separate question from its output's.

## Notice-survival mechanics

Rust has no standard minification step comparable to JavaScript's, and
comments are not present in compiled artifacts, so the source-level
comment-stripping concern does not apply to a built binary. The mechanism
that can drop a notice instead is **publishing**: `cargo package`/`cargo
publish` includes only the files Cargo determines belong in the package,
governed by the `include`/`exclude` fields in `Cargo.toml` (or, absent those,
a default that follows version-control tracking). A file named by
`license-file` is always included regardless of those fields, but that
guarantee is narrow and does not reach the notices most crates actually
carry: the prevailing dual-licence layout declares the `license` SPDX
expression and ships `LICENSE-APACHE` and `LICENSE-MIT` on disk with no
`license-file` field at all, so both texts are governed by `include`/
`exclude` like any other file. The same applies to a `NOTICE` file and to
third-party licence texts under a vendored path. Confirm every notice the
distribution actually requires is packaged, not merely present in the
repository.

## Mark surfaces

The `[package] name` field in `Cargo.toml` is the crate's identity on
crates.io and the most common location for a third-party project or
organization mark to appear verbatim. A `User-Agent` string literal set on an
HTTP client (`reqwest`, `hyper` construction) and a CLI `--version`/banner
string — often derived from `CARGO_PKG_NAME`/`CARGO_PKG_VERSION` build-time
environment variables via a crate such as `clap` — are the other recurring
surfaces, per `source-code.md`'s "Marks in code" class (`IP-MARK-1`,
`IP-MARK-2`).

## Criteria

This pack carves out no core criterion and adds none; it applies the core
`IP-LIC-*`, `IP-SRC-*`, `IP-COPY-*`, and `IP-MARK-*` criteria via the facts
above, including `IP-LIC-4` for the dual-licence selection. No `rust.IP-*`
numbered criterion is defined.
